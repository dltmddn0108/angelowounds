# 테스트 전략

소프트웨어 테스트는 피라미드 구조로 접근해야 한다. 아래에서 위로: 단위 테스트 > 통합 테스트 > E2E 테스트.

## 단위 테스트 (Unit Test)

개별 함수나 모듈을 독립적으로 테스트한다. 빠르고 안정적이어야 한다.

```typescript
// vitest example
describe('calculateDiscount', () => {
  it('applies 10% for orders over 100', () => {
    expect(calculateDiscount(150)).toBe(15);
  });

  it('returns 0 for orders under 100', () => {
    expect(calculateDiscount(50)).toBe(0);
  });
});
```

## 통합 테스트 (Integration Test)

여러 모듈이 함께 동작하는 것을 확인한다. 데이터베이스, API 호출 등 외부 의존성을 포함. Docker로 테스트 환경을 구성하면 일관된 결과를 얻을 수 있다.

## E2E 테스트

사용자 시나리오 전체를 테스트한다. Playwright나 Cypress를 사용. 느리고 불안정할 수 있으므로 핵심 플로우만 커버하는 것이 좋다.

## 테스트 커버리지

80%를 목표로 하되 숫자에 집착하지 말 것. 커버리지보다 중요한 것은 의미 있는 테스트를 작성하는 것이다.

> [!info] TDD 팁
> Red-Green-Refactor 사이클을 따르면 자연스럽게 테스트 가능한 코드가 작성된다. 함수형 프로그래밍 원칙을 적용하면 테스트가 훨씬 쉬워진다.
